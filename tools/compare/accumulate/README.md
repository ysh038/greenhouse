# 누적 비교 시험 재료

화면이 쌓일 때 프레임워크가 있을 때와 없을 때가 어떻게 달라지는지 본 시험(실전 시험 6회)에 쓴 재료입니다. 화면 하나를 비교한 5회차 재료(`tools/compare`의 나머지)를 그대로 이어 씁니다.

## 순서

1. 5회차의 결과물(식물 재고 화면이 들어 있는 앱)을 출발점으로 삼습니다. 조건마다 여럿을 둡니다(체인).
2. 가짜 서버를 `specs/fakeApi.body.ts`로 바꿉니다. 첫 줄에 `createFakeApi`를 가져오는 import만 조건에 맞게 붙입니다.
3. 체인마다 맥락 없는 새 에이전트에게 `spec-2-orders.md`, `spec-3-suppliers.md`, `spec-4-settings.md`를 차례로 줍니다. 에이전트는 앞사람이 남긴 코드를 이어받습니다.
4. 네 화면이 쌓인 뒤 `spec-5-change.md`(네 화면에 걸친 변경 세 가지)를 줍니다.
5. 단계가 끝날 때마다 폴더를 통째로 복사해 두고(스냅숏), 채점과 측정은 스냅숏에서 돌립니다.

## 파일

| 위치 | 내용 |
|---|---|
| `specs/spec-*.md`, `tail*.md` | 과제 지시문. `{{SRC}}`, `{{PROJECT_DIR}}`, `{{PORT}}` 자리만 바꿔 넣습니다 (`scripts/make-prompts.sh`) |
| `specs/fakeApi.body.ts` | 네 화면의 경로가 모두 든 가짜 서버 |
| `screens.mjs` | 화면 2~4 채점 57개 (화면마다 적힌 요구와 적지 않은 견고성) |
| `change.mjs` | 공통 변경 채점 32개 (주 색상 14, 실패 문구 10, 포커스 8)와 참고 항목 1개 |
| `probe.mjs` | 같은 역할의 요소가 화면마다 같은 모양인지 측정하고 스크린샷을 찍음 |
| `static.mjs` | 코드 측정 (줄 수, 직접 쓴 색, Effect·리스너·타이머, 화면 사이의 중복) |
| `sheet.mjs` | 조건을 가린 평가에 쓸 스크린샷 모아 보기 |
| `lib.mjs`, `flows.mjs` | 위 스크립트가 같이 쓰는 도우미 |
| `scripts/` | 여섯 체인에 채점을 차례로 돌리는 셸 스크립트와 수정량 계산 |

화면 1(식물 재고)은 5회차의 `../accept.mjs`로 채점합니다.

## 실행

저장소 루트에서 실행합니다. 설치된 Chrome을 씁니다.

```bash
node tools/compare/accumulate/screens.mjs <앱 폴더> <결과 폴더> <포트> [검사 id 앞글자...]
```

```bash
node tools/compare/accumulate/change.mjs <앱 폴더> <결과 폴더> <포트> [변경 전 probe.json]
```

```bash
node tools/compare/accumulate/probe.mjs <앱 폴더> <결과 폴더> <포트>
```

```bash
node tools/compare/accumulate/static.mjs <제품 코드 폴더(src)> [이름]
```

## 채점 스크립트를 믿기 전에

이 스크립트들은 구현을 모르는 채로 화면만 보고 검사하므로, 구현 방식이 예상과 다르면 틀리게 채점합니다. 6회차에서 실패로 나온 것 가운데 스크립트 오류였던 것:

- 식물 이름("유칼립투스")으로 식물 재고 화면인지 판단했는데, 주문 목록에도 같은 이름이 나옴
- 빈 목록을 한 번만 돌려주게 했는데, 같은 조회를 두 번 보내는 구현이 있음
- 변경 요청 실패를 여섯 번 걸어 뒀더니, 실패 뒤 목록을 다시 받는 구현에서 그 조회까지 실패함
- 고른 필터의 색을 라디오 입력과 라벨에서만 찾았는데, 숨긴 라디오 옆의 요소를 꾸미는 구현이 있음
- 예전 주 색상이 남은 곳을 셌는데, 성공·상태 색이 예전 주 색상과 같은 값이라 걸림 (참고 항목으로 뺌)

실패가 나오면 구현 탓으로 적기 전에 화면에서 직접 확인합니다.
