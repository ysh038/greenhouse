# agent-greenhouse

에이전트가 쓴 코드를 믿을 수 있게 만드는 React FE용 프레임워크입니다. 까다로운 처리를 한 번만 제대로 만든 API와, 제품 코드가 그 API만 쓰도록 강제하는 린트 규칙을 한 세트로 쌓습니다.

온실이 식물이 자라는 환경을 통제하듯, 에이전트가 일하는 환경(코드베이스)을 통제한다는 뜻에서 붙인 이름입니다.

## 배경

발표 ["모든 코드는 슬롭이다, 내 것만 빼고"](https://www.youtube.com/watch?v=ueA116hO_ho)의 역피라미드에서 출발했습니다. 에이전트 환경에 들이는 시간은 코드베이스와 정적 분석에 가장 많이, 규칙 파일 같은 산문에 가장 적게 써야 한다는 내용입니다.

이 저장소의 원칙은 하나입니다. **에이전트를 교정할 일이 생기면 규칙 파일에 한 줄 보태지 않고, 린트 규칙이나 API 설계로 옮깁니다.**

기능 하나는 아래 세 가지가 한 세트입니다.

1. **안전한 API**: 까다로운 처리를 한 번만 제대로 만든 것
2. **금지 규칙**: 제품 코드에서 원본을 직접 못 쓰게 하는 린트. 에러 메시지가 대안을 알려 줍니다.
3. **구역 구분**: 폴더로 프레임워크 구역과 제품 구역을 나눈 것

## 시작하기

```bash
pnpm install
```

```bash
pnpm check
```

`pnpm check`는 피어 의존성, 타입 검사, 린트, 위반 예제, 테스트, 샘플 앱 빌드, 화면 검증을 차례로 돌립니다.

```bash
pnpm verify
```

`pnpm verify`는 화면 시나리오(`*.verify.ts`)를 실제 브라우저에서 돌려 `evidence/`에 스크린샷과 보고서를 남깁니다. 시나리오마다 밝은 화면, 어두운 화면, 좁은 화면 세 조건으로 돌립니다. `pnpm verify invites`처럼 경로 일부를 주면 그 시나리오만 돌립니다.

서버가 정상일 때는 볼 수 없는 화면은 시나리오에서 요청을 가로채서 만듭니다. 검증 도구가 띄운 브라우저에서 나가는 요청만 바꾸므로 앱 코드와 서버는 그대로입니다.

```ts
const loading = await page.hold('GET /api/tasks') // 붙잡아 둠: "불러오는 중"
await page.reload()
await page.shot('불러오는 중')
await loading.stop()

const failing = await page.fail('GET /api/tasks') // 실패 응답(기본 500)
const empty = await page.respond('GET /api/tasks', { body: [] }) // 다른 응답으로 대신함
```

가로채기는 `stop()`을 부를 때까지 그 요청을 계속 가로챕니다. 화면이 실패한 요청을 다시 보내도 같은 결과가 나옵니다.

### 스크린샷 검토

`pnpm verify`는 새로 생겼거나 달라진 스크린샷이 있으면 실패로 끝나고, 그것들을 모아 보기(`evidence/review/*.png`)로 만들어 줍니다. 모아 보기를 한 장씩 열어 모양을 확인한 뒤 기록합니다.

```bash
pnpm verify:review TaskSection-1 <확인 코드> "<무엇을 확인했는지>"
```

- 확인 코드는 모아 보기 그림 위쪽에만 적혀 있습니다. 그림을 열어야 알 수 있습니다.
- 기록한 스크린샷은 `evidence/reviewed/`에 사본으로 남습니다. 다음 실행부터는 사본과 눈에 띄게 다른 것만 다시 검토를 요구합니다. 화면 하나를 고치면 그 화면의 스크린샷만 나옵니다.
- 잘림, 겹침, 어긋난 정렬이 보이면 기록하지 않고 고친 뒤 다시 돌립니다.
- 검토 기록은 커밋하지 않습니다(`evidence/`). 저장소를 새로 받은 컴퓨터에서는 처음 한 번 전부 검토해야 `pnpm check`가 통과합니다.

### PR에 증거 붙이기

```bash
pnpm verify:attach
```

현재 브랜치의 PR 본문에, 이 브랜치에서 검토한 모아 보기와 검토 기록을 붙입니다. 다시 돌리면 붙인 구역만 새로 바꿉니다.

- 그림은 `main`에 합쳐지지 않는 브랜치(`verify-evidence/<PR 번호>`)에 올리고, 본문에서는 그 커밋의 그림을 가리킵니다. `main`의 이력에는 그림이 들어가지 않습니다.
- `pnpm verify:attach --clean`은 머지되거나 닫힌 PR의 그림 브랜치를 지우고, 본문에는 검토 기록만 남깁니다. 열려 있는 PR의 것은 남깁니다.
- 지금은 GitHub만 지원합니다(`gh` 필요). PR이 없는 브랜치에서는 아무것도 하지 않으므로, `main`에 바로 올리는 작업 방식은 그대로입니다.
- 브랜치를 지운 직후에도 그림 주소는 한동안 열립니다. GitHub가 어디에서도 가리키지 않는 커밋을 정리할 때까지입니다.

### 화면마다 시나리오

`src/<기능>/` 폴더에 화면 코드(`.tsx`)가 있는데 시나리오(`*.verify.ts`)가 하나도 없으면 `pnpm verify`가 그 폴더를 문제로 보고합니다. 스크린샷을 한 장도 남기지 않는 시나리오도 문제로 봅니다. 여러 기능이 같이 쓰는 코드를 두는 `src/shared/`는 이 검사에서 빠집니다.

폴더 단위로만 봅니다. 시나리오가 있는 폴더에 화면 파일을 더했을 때 그 화면까지 시나리오가 다루는지는 검사하지 못합니다.

```bash
pnpm deps:update
```

`pnpm deps:update`는 오래된 의존성을 하나씩 최신으로 올리고 `pnpm check`를 돌립니다. 실패하는 것은 되돌리고 보류 목록으로 알려 줍니다.

## 지금까지 확인된 것과 아닌 것

5회차와 6회차 시험에서 같은 모델(Opus)이 프레임워크가 있을 때와 없을 때 각각 무엇을 만드는지 비교했습니다. 5회차는 화면 하나를 조건마다 3번, 6회차는 그 결과물 위에 서로 다른 에이전트가 화면 세 개를 차례로 더 쌓고 네 화면에 걸친 변경을 하나 시켰습니다.

- **동작 품질은 두 번 모두 차이가 없었습니다.** 화면 하나일 때 채점 24개, 화면 네 개일 때 81개, 공통 변경 32개를 여섯 체인이 모두 통과했습니다.
- **프레임워크 쪽이 더 비쌌습니다.** 화면 하나일 때 토큰 약 1.5배, 화면을 더할 때 약 1.1배, 공통 변경에서 약 1.2배입니다.
- **프레임워크 없는 쪽이 스스로 정리했습니다.** 두 번째 화면부터 모달, 색 변수, HTTP 호출을 공용으로 뺐습니다. 직접 쓴 `useEffect`와 색의 가짓수는 화면이 늘어도 늘지 않았습니다.
- **공통 변경도 프레임워크 쪽이 유리하지 않았습니다.** 주 색상 변경은 두 조건 모두 파일 하나였습니다.
- **프레임워크에 없는 것(모달, 위험한 동작용 버튼)은 체인마다 다르게 만들어졌습니다.**
- **화면 평가로는 두 조건을 가를 수 없었습니다.** 조건을 가린 평가자 두 명의 방향이 서로 반대였습니다.

Opus가 화면 네 개까지 차례로 쌓는 범위에서는 이 프레임워크가 품질이나 변경 비용을 낫게 한다는 근거가 없습니다.

7회차에서는 Sonnet 에이전트 셋이 서로를 보지 못한 채 화면을 하나씩 동시에 만들고, 네 번째가 합쳤습니다. 조건마다 한 번씩 돌렸습니다.

- **동작 품질은 이번에도 같았습니다.** 두 조건 모두 채점 57개 중 56개를 통과했고 떨어진 항목도 같습니다.
- **화면 사이의 모양이 처음으로 갈렸습니다.** 프레임워크 없는 쪽은 세 화면의 "저장" 버튼이 8가지 속성 중 7가지에서 서로 달랐고, 프레임워크 쪽은 모두 같았습니다. 프레임워크 없는 쪽은 합친 뒤에도 모달 구현이 두 벌 남았습니다.
- **프레임워크 쪽이 토큰을 1.8배 썼습니다.**
- **원인이 모델인지 동시 작업인지는 가르지 못했습니다.** 6회차와 견주면 둘이 같이 바뀌었습니다.

8회차에서는 한 화면이 다른 화면의 데이터와 코드를 쓰게 되는 과제를 Sonnet에게 조건마다 세 번 시켰습니다.

- **구조 규칙이 막으려던 코드가 처음 관측됐습니다.** 규칙이 없는 조건의 세 실행 가운데 하나가 화면 폴더끼리 서로를 직접 가져왔습니다(6건). 규칙이 있는 조건은 세 실행 모두 `shared`로 옮겼습니다.
- **동작 품질은 같았고, 프레임워크 쪽이 토큰을 1.85배 썼습니다.**
- **프레임워크의 빈 곳이 드러났습니다.** 조회 여러 개를 동시에 시작하는 수단, 오래된 캐시가 잠깐 보이는 것을 막는 수단, 특정 요청만 실패시키는 테스트 도우미가 없습니다.

아직 재지 않은 조건은 한 번에 읽을 수 없을 만큼 큰 코드베이스와 나쁜 예제가 있는 기존 코드입니다. 자세한 내용은 [5회차](docs/trial-5-2026-11-18.md), [6회차](docs/trial-6-2026-11-19.md), [7회차](docs/trial-7-2026-11-25.md), [8회차](docs/trial-8-2026-11-25.md) 시험 문서에 있습니다.

### 2단계 모듈 후보

측정 결과에서 근거가 많은 순서입니다.

- **Effect 모듈 (완료)**: `useEventListener`, `useClickOutside`, `useKeydown`, `useTimeout`, `useInterval`, `useDebouncedValue`, `useAnimationFrame`. 제품 코드에서 `useEffect`, 타이머, `addEventListener`를 금지합니다. 크기 측정이나 스크롤 맞추기처럼 아직 훅이 없는 용도는 실전 시험에서 필요가 확인되면 추가합니다.
- **데이터 모듈 (완료)**: `createApiClient`(응답 스키마 필수), `defineQuery`와 `useData`, `defineMutation`과 `useMutate`, `DataBoundary`, `DataProvider`. 제품 코드에서 `axios`, `fetch`, `@tanstack/react-query` 직접 사용을 금지합니다. 검색처럼 인자가 자주 바뀌는 조회는 `useDeferredData`를 씁니다. 조건부 조회, 무한 스크롤, 낙관적 갱신은 아직 없고 실전 시험에서 필요가 확인되면 추가합니다.
- **가짜 서버와 테스트 도우미 (완료)**: `fake-api`의 `createFakeApi`(지연, 한 번 실패, 요청 기록)와 `testing`의 `renderWithData`, `advanceTime`, `connectFakeApi`(테스트 동안 `fetch`를 가짜 서버에 연결). 실전 시험에서 에이전트가 직접 만들어 쓰던 것을 프레임워크로 옮겼습니다.
- **UI 모듈 (완료)**: 디자인 토큰(CSS 변수, 다크 모드 포함)과 `Button`(되돌릴 수 없는 동작은 `tone="danger"`), `TextField`(옆에 붙는 버튼은 `trailing`), `Checkbox`, `Stack`, `Card`, `Text`, `Page`, `ErrorNotice`, `Select`(여럿 가운데 하나 고르기), `Dialog`(화면 위에 뜨는 창), `ConfirmDialog`(하기 전에 묻는 창). 제품 코드에서 생 `<button>`, `<input>`, `<select>`, 고정 값 인라인 `style`, `div` 같은 요소의 `onClick`, 직접 만든 모달(`<dialog>`, `role="dialog"`, `aria-modal`, `window.confirm`)을 금지합니다. 실행 중에 정해지는 값은 `style`에 쓸 수 있습니다. 라디오는 아직 없고 실전 시험에서 필요가 확인되면 추가합니다. `Select`는 브라우저의 기본 select를 감싼 것입니다. 모달은 포커스 가두기, Escape와 바깥 클릭으로 닫기, 닫은 뒤 포커스 되돌리기를 처리합니다. 뒤 화면을 `inert`로 막거나 스크롤을 잠그지는 않습니다. 컴포넌트로 안 되는 고정 값은 제품 폴더의 CSS 모듈에 쓰고, 그 CSS는 stylelint로 검사합니다: 요소 선택자와 `*` 금지(컴포넌트 모양을 바깥에서 덮어쓰지 못하게), hex 색상 금지, 토큰과 같은 px 값 금지.
- **라우터 모듈 (완료)**: 주소에 따라 화면을 바꿉니다. `defineRoute('/plants/:id')`로 주소를 정의하고 `route.href({ id })`로 만듭니다. `AppRouter`로 앱을 감싸고 `RouteView(routes, notFound)`가 지금 주소의 화면을 그립니다. 누르는 링크는 `Link`(메뉴 항목은 `appearance="nav"`, 지금 화면이면 `aria-current`), 앱 밖으로는 `ExternalLink`, 코드에서 옮길 때는 `useNavigate`, 주소의 값은 `useRouteParams(route)`, 필터나 정렬처럼 주소에 둘 상태는 `useSearchParam`을 씁니다. 제품 코드에서 `react-router` 직접 사용과 생 `<a>`를 금지합니다. 이 두 금지 규칙은 위반이 관측된 적 없이 넣었습니다. 로그인해야 들어갈 수 있는 화면은 `defineAccess<역할>()`로 만든 `AccessProvider`와 `ProtectedRoute`로 감쌉니다. 확인 중이면 기다리고, 로그인하지 않았으면 돌아올 주소와 함께 로그인 화면으로 보내고, 역할이 맞지 않으면 정해 둔 화면으로 보냅니다. 로그인 화면은 `useLoginReturn`으로 돌아갈 주소를 읽습니다. 로그인 상태 자체(토큰 보관, 갱신)는 앱이 만들어 넘깁니다. 팀의 기존 프로젝트들이 화면마다 복사해 쓰던 것을 옮긴 것이고, 화면을 가리는 것일 뿐이라 서버도 같은 권한을 검사해야 합니다. 화면을 감싸는 공통 틀(중첩 화면), 화면을 떠나기 전에 묻기, 화면별 코드 나눠 받기, 스크롤 위치 되돌리기는 없습니다. 테스트에서는 `renderWithData(ui, { path })`로 그 주소에서 연 것처럼 그리고, 화면 시나리오는 `path`로 여는 주소를 정합니다.
- **주석 금지 (제품 구역 규칙)**: 제품 코드(`apps/**`)에는 주석을 쓰지 않습니다(`product/no-comments`). JSX 안의 주석도 포함입니다. 테스트(`*.test.ts(x)`), 화면 시나리오(`*.verify.ts`), 가짜 서버(`fake` 폴더)는 대상이 아닙니다. 무엇을 왜 확인하는지, 어떤 API가 있는지 적은 주석이 그 파일의 내용이기 때문입니다. 무엇을 하는지는 이름으로, 왜 그렇게 했는지는 테스트 이름으로 남깁니다. `pnpm exec eslint --fix <파일>`로 한 번에 지울 수 있습니다. 프레임워크 구역은 대상이 아닙니다. 프레임워크 API의 설명 주석은 에이전트가 사용법을 찾는 자리라서 그대로 둡니다. 제품 구역의 CSS 주석은 막지 않습니다. 이 규칙은 에이전트의 주석이 문제를 일으킨 사례를 세어 보지 않고 넣었습니다.
- **구조 모듈 (완료)**: 제품 앱의 `src` 바로 아래 폴더 하나를 기능 하나로 봅니다. 기능 폴더는 자기 폴더, `src/shared/`, `src`에 바로 놓인 파일만 가져올 수 있고, 다른 기능 폴더는 가져올 수 없습니다(`structure/no-cross-feature-import`). `src/shared/`는 기능 폴더를 가져올 수 없습니다. `App.tsx`처럼 `src`에 바로 놓인 파일은 기능들을 조합하는 자리라 제한이 없습니다. 상대 경로와 `@/` 별칭을 봅니다. 다른 별칭은 보지 못합니다. API는 없고 규칙만 있는 모듈입니다. 이 규칙은 위반이 관측된 적 없이 넣었고, 8회차 시험에서 처음 관측됐습니다: 규칙이 없는 조건의 세 실행 가운데 하나가 화면 폴더끼리 서로를 가져왔습니다(6건). 규칙이 있는 조건의 에이전트는 README에서 규칙을 읽고 처음부터 `shared`로 옮겨서, 린트 에러 메시지로 고쳐지는 장면은 아직 관측되지 않았습니다. 기능의 공개 진입점(`index.ts`)만 가져오게 하는 규칙과 파일 크기 제한은 넣지 않았습니다.

모듈은 자기 폴더만 건드리므로 여러 세션이 동시에 작업할 수 있습니다.

### 아직 정하지 않은 것

- 검증 증거를 PR에 붙이는 장치(`pnpm verify:attach`)를 GitLab에서도 쓸 수 있게 할지. 지금은 GitHub만 됩니다. 비공개 저장소에서 그림이 권한 있는 사람에게 보이는지도 아직 확인하지 않았습니다(공개 저장소에서만 시험).
- 스크린샷을 봐야 한다는 것은 검토 기록으로 강제합니다(4회차에서 에이전트는 24장 중 4장만 봤습니다). 다만 확인 코드는 모아 보기를 열었다는 것까지만 보장하고, 꼼꼼히 봤는지는 보장하지 못합니다. 이 장치가 결함을 실제로 더 잡는지는 시험해 보지 않았습니다.
- 하나만 고르는 필터. 4회차에서 한 번 필요가 관측됐습니다. 같이 관측된 위험한 동작용 버튼과 모달은 만들었습니다. 같이 관측된 가짜 서버 데이터 되돌리기는 테스트마다 가짜 서버를 새로 만드는 것으로 해결했습니다.

- 샘플 앱 주제. 실제로 만드는 화면과 비슷할수록(목록, 상세, 폼, 로그인) 실전 시험이 쓸모 있습니다.
- `pnpm deps:update`를 주기적으로 돌리는 장치(CI 예약 실행).
- 제품 CSS 검사의 범위. 지금은 3회차 시험과 측정에서 관측된 것만 막습니다. `rgb()`나 색 이름으로 쓴 색, 토큰에 없는 px 값(`13px`), CSS로 직접 한 배치(`display: flex`), 속성 선택자로 컴포넌트를 덮어쓰는 것은 통과합니다.
- `Button`을 줄 전체 너비로 왼쪽 정렬하는 수단을 넣을지. 3회차에서 한 번 필요가 관측됐습니다.

### 알아 둘 것

- TypeScript는 6.0에 머뭅니다. 7.0이 나와 있지만 typescript-eslint 8.73이 6.1 미만만 지원합니다. 지원이 추가되면 `pnpm deps:update`가 올립니다.
- `eslint-plugin-react` 7.37은 ESLint 10을 공식 지원 범위에 넣지 않았지만 동작합니다. `pnpm-workspace.yaml`에서 예외로 허용했고, 이 플러그인의 규칙은 위반 예제로 동작을 확인합니다.
- 라우터 모듈은 react-router 8을 감쌉니다. React Compiler는 아직 넣지 않았습니다.
- HTTP 요청은 axios가 아니라 `fetch` 위에 만들었습니다. 응답 검증은 zod를 씁니다.
- 샘플 앱은 진짜 백엔드가 있는 프로젝트처럼 실제 HTTP 요청을 보냅니다. 백엔드가 없어서 개발 서버가 `/api` 요청을 받아 가짜 서버(`apps/sample/src/shared/fake`)로 넘깁니다(`apps/sample/fakeServer.plugin.mjs`). 응답은 400ms 늦게 오고, 데이터는 개발 서버를 다시 띄우거나 가짜 서버 파일을 고칠 때 처음 상태로 돌아갑니다. 백엔드가 있는 프로젝트에는 이 플러그인이 필요 없습니다.
- 테스트에서는 요청이 네트워크로 나가지 않습니다. `connectFakeApi(createFakeServer())`가 `fetch`를 테스트마다 새로 만든 가짜 서버에 연결합니다.
- 화면 검증은 실행마다 `x-verify-run` 헤더에 다른 값을 넣어 보냅니다. 샘플 앱의 가짜 서버는 이 값마다 데이터를 따로 두어, 동시에 도는 세 화면 조건이 서로 영향을 주지 않습니다.
- `vite build`로 만든 샘플 앱에는 `/api`를 받아 줄 서버가 없습니다. 빌드는 빌드가 되는지만 확인합니다.
- 샘플 앱은 `pnpm --filter @agent-greenhouse/sample dev`로 띄웁니다.
- 화면 검증은 개발 서버를 비어 있는 포트에 띄웁니다. 여러 작업이 동시에 돌려도 포트가 겹치지 않습니다. 다만 `evidence/`는 저장소 폴더마다 하나라서, 같은 폴더에서 동시에 두 번 돌리면 결과가 섞입니다.
- 화면 검증은 이 컴퓨터에 설치된 Chrome을 씁니다. 브라우저를 따로 내려받지 않습니다. 다른 브라우저는 `VERIFY_BROWSER=msedge`처럼 지정합니다. Chrome이 없으면 `pnpm check`의 마지막 단계가 실패합니다.
- 스크린샷 검토는 쓸 수 있는 가장 큰 모델에게 맡깁니다. 4회차 시험에서 Opus만 없는 문제를 지어내지 않았고 심지 않은 실제 버그를 찾았습니다. 작은 모델은 린트 메시지처럼 결정적인 안내를 따르는 일에는 충분했지만 눈으로 보는 검토에서는 차이가 났습니다.
- 화면 검증이 자동으로 잡는 것은 단계 실패(대상을 못 찾음, 대상이 여럿), 예상하지 않은 콘솔 에러와 서버의 실패 응답(400 이상), 가로 넘침, 가로채도록 했는데 오지 않은 요청입니다. 시나리오가 일부러 내는 실패 응답은 `expectedConsoleErrors`에 `'응답 400: POST /api/tasks'`처럼 적습니다. 모양이 맞는지는 스크린샷을 사람이나 에이전트가 봐야 압니다. `evidence/`는 커밋하지 않습니다.
- 같은 화면을 다시 찍어도 세로로 긴 스크린샷은 픽셀 몇백 개가 조금씩 달라집니다(색 차이 16 이하로 측정). 그래서 검토한 사본과의 비교는 색 차이가 24를 넘는 픽셀이 8개 이하이고, 조금이라도 다른 픽셀이 전체의 0.05% 이하일 때 같은 것으로 봅니다. 색 차이가 24를 넘는 픽셀을 처음에는 하나도 허용하지 않았는데, 화면을 바꾸지 않은 실행에서 같은 스크린샷의 2픽셀이 달라져 실패한 일이 세 번 있어서 8개까지 허용했습니다. 이보다 옅은 변화는 다시 검토를 요구하지 않습니다.
- `pnpm deps:update`는 의존성을 올린 뒤 화면이 달라지면 검토가 남아 `pnpm check`가 실패하므로, 그 의존성을 보류 목록에 넣습니다. 올리려면 직접 올린 뒤 스크린샷을 검토합니다.
- UI 모듈을 가져오면 토큰과 기본 스타일(`body`, 제목, 목록의 여백과 글꼴)이 전역으로 들어갑니다. 따로 불러올 CSS는 없습니다.
- stylelint 18은 Node 22.22 이상, 24.15 이상, 26 이상을 공식 지원합니다. 이 저장소를 만든 컴퓨터의 Node 23.10은 그 범위 밖이지만 동작합니다.
- UI 컴포넌트는 `className`과 `style`을 받지 않습니다. 모양은 `variant`, `tone`, `gap` 같은 속성으로만 고릅니다.
