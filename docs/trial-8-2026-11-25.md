# 실전 시험 8회: 화면이 서로 엮일 때 (2026-11-25)

구조 규칙(`structure/no-cross-feature-import`)은 위반이 관측된 적 없이 들어가 있었습니다. 7회차까지의 과제는 화면이 서로의 코드를 쓸 일이 없어서, 0건이 "에이전트가 그런 코드를 쓰지 않는다"는 뜻인지 "쓸 상황이 없었다"는 뜻인지 알 수 없었습니다. 이번에는 **한 화면이 다른 화면의 데이터와 코드를 쓰고 싶어지는 과제**를 줬습니다. 모델은 Sonnet입니다.

## 요약

- **구조 규칙이 막으려던 코드가 처음 관측됐습니다.** 규칙이 없는 조건의 세 실행 가운데 하나가 화면 폴더끼리 서로를 직접 가져왔습니다(양방향, 6건). 나머지 둘은 스스로 `shared` 폴더로 옮겼습니다.
- **규칙이 있는 조건은 세 실행 모두 `shared`로 옮겼습니다.** 다만 린트 에러가 난 적은 없습니다. 세 에이전트 모두 README에서 규칙을 읽고 처음부터 그렇게 배치했습니다.
- **동작 품질은 같았습니다.** 적힌 요구 10개는 여섯 실행이 모두 통과했고, 기존 채점 57개도 여섯 실행이 모두 56개로 같습니다.
- **프레임워크 쪽이 토큰을 1.85배 썼습니다.** 7회차와 같은 수준입니다.
- **프레임워크의 빈 곳 세 개가 드러났습니다.** 조회 여러 개를 동시에 시작하는 수단, 오래된 캐시가 잠깐 보이는 것을 막는 수단, 특정 요청만 실패시키는 테스트 도우미입니다.

## 시험 방법

### 구성

7회차에서 합친 앱(주문, 공급처, 알림 설정)을 조건별 출발점으로 썼습니다. A는 프레임워크가 있고 구조 규칙이 켜져 있습니다. B는 프레임워크가 없습니다. 조건마다 맥락 없는 Sonnet 에이전트 셋이 같은 과제를 각자 했습니다(A1~A3, B1~B3).

과제는 세 화면을 서로 잇는 것입니다(`tools/compare/linked/spec.md`).

| 바꿀 것 | 필요해지는 것 |
|---|---|
| 주문 목록과 상세에 공급처 이름과 연락처 | 주문 화면이 공급처 데이터를 씀 |
| 주문 화면에 "새 주문 알림이 켜져 있습니다" 문장 | 주문 화면이 알림 설정 데이터를 씀 |
| 공급처마다 "주문 2건"과 "주문 보기" 창(주문 목록과 상태) | 공급처 화면이 주문 데이터와 상태 문구를 씀 |
| 한 화면에서 바꾼 것이 새로고침 없이 다른 화면에 반영 | 화면 사이의 데이터 일관성 |

서버는 주문에 `supplierId`만 주고 공급처 이름이나 주문 수는 주지 않습니다. 지시문에는 코드를 어디에 두라는 말을 넣지 않았고, "기존 코드는 고쳐도 되고 옮겨도 됩니다"라고만 적었습니다.

### 채점과 측정

- **새 동작 12개**: 적힌 요구 10개와 견고성 2개(`tools/compare/linked/accept.mjs`).
- **기존 57개**: 6회차의 화면 채점을 그대로 돌려 깨진 것이 없는지 봤습니다.
- **구조**: 프레임워크의 구조 규칙을 B의 코드에도 돌려 화면 폴더 사이의 import를 셌습니다.
- `pnpm check`는 여섯 실행 모두 진행자가 직접 다시 돌렸습니다.

## 결과

### 구조

| | A1 | A2 | A3 | B1 | B2 | B3 |
|---|---|---|---|---|---|---|
| 화면 폴더 사이의 import | 0 | 0 | 0 | 0 | **6** | 0 |
| `shared`로 옮긴 것 | 조회와 스키마 | API 파일 4개 | API 파일 4개 | API 파일 4개 | 없음 | API 파일 4개 |

- **B2의 6건은 양방향입니다.** `orders`의 두 파일이 `suppliers/suppliersApi`와 `settings/settingsApi`를 가져오고, `suppliers`의 두 파일이 `orders/ordersApi`와 `orders/statusLabels`를 가져옵니다. 주문 화면과 공급처 화면이 서로에게 기대는 구조입니다.
- **B1과 B3은 규칙 없이도 옮겼습니다.** B1의 보고서는 이유를 "orders와 suppliers 폴더가 서로를 import하는 순환이 생깁니다"라고 적었습니다.
- **A의 셋은 린트에 걸리지 않고 옮겼습니다.** 세 보고서 모두 구조 규칙의 이름을 들어 배치 이유를 설명했습니다. 규칙의 에러 메시지가 에이전트를 고치게 하는 장면은 이번에도 관측되지 않았습니다. 효과가 났다면 README의 설명을 통해서입니다.
- A1은 여러 화면이 읽는 조회만 옮기고 변경 요청은 각 화면 폴더에 남겼습니다. 나머지 넷은 API 파일을 통째로 옮겼습니다.

### 채점 스크립트를 고친 것

처음 돌렸을 때 떨어진 항목 가운데 넷은 스크립트 쪽 문제였고, 고친 뒤 여섯 실행에 다시 돌렸습니다. 위 표는 고친 뒤의 값입니다.

- **창 안의 글자 찾기**: 제목에서 위로 올라가며 "닫기" 버튼을 품은 첫 조상을 창으로 봤는데, 프레임워크의 `Dialog`는 제목 줄에 "닫기"가 있어서 제목 줄만 잡혔습니다. A의 셋이 모두 두 항목에서 떨어졌습니다.
- **빈 목록 만들기**: 기존 채점이 "다음 요청 몇 개"를 빈 목록으로 바꿨는데, 주문 화면이 이제 공급처와 설정도 받아서 그 요청까지 바뀌었습니다. B의 셋이 떨어졌습니다.
- **"다시 시도" 누르기**: 기존 채점이 "다시 시도" 버튼 하나를 눌렀는데, A2와 A3은 알림 설정 문장에도 "다시 시도"가 있어서 그쪽이 눌렸습니다. 화면에 "다시 시도"가 둘 보이는 것 자체는 사용자에게도 헷갈릴 수 있는 점입니다.

## 드러난 프레임워크의 빈 곳

- **조회 여러 개를 동시에 시작할 수 없습니다.** 한 컴포넌트가 `useData`를 두 번 부르면 앞 응답이 온 뒤에야 뒤 요청이 나갑니다. A의 셋이 모두 보고했고, A2는 빈 컴포넌트를 형제로 두어 먼저 시작하게 하는 우회책(`PreloadData`)을 만들었습니다.
- **오래된 캐시가 잠깐 보입니다.** 다른 화면에서 값을 바꾸고 돌아오면 이전 값이 먼저 나왔다가 바뀝니다. A의 셋이 모두 보고했고 막을 수단이 없다고 했습니다. 채점은 최종 상태만 보므로 이 깜빡임은 측정하지 않았습니다.
- **특정 요청만 실패시키는 테스트 도우미가 없습니다.** `failOnce`는 다음에 오는 요청이 무엇이든 실패시킵니다. 화면이 요청을 여러 개 보내자 기존 테스트가 깨졌고, 여섯 에이전트 가운데 다섯이 주소로 골라 실패시키는 도우미를 각자 만들었습니다. 채점 스크립트도 같은 문제에 걸렸습니다.
- **한 조회의 실패가 화면 전체를 막습니다.** 공급처 조회가 실패하면 주문 목록도 보이지 않습니다. A의 셋 모두 그랬습니다.

## 한계

- **조건마다 세 번입니다.** "규칙이 없으면 셋 중 하나"는 비율로 읽을 수 없습니다. 위반이 실제로 나온다는 것만 확인했습니다.
- **규칙의 효과와 README의 효과를 가르지 못했습니다.** A의 에이전트는 린트에 걸리기 전에 README에서 규칙을 읽었습니다. README에 설명 없이 린트만 켰을 때 에러 메시지로 고쳐지는지는 보지 않았습니다.
- **출발점이 조건마다 다릅니다.** 7회차에서 각 조건이 만든 앱을 이어받았으므로, 이번 차이에는 7회차의 차이가 섞여 있습니다.
- **위반이 나쁜 결과로 이어지는지는 보지 않았습니다.** B2는 화면끼리 서로를 가져왔지만 동작 채점은 가장 높았습니다. 이 구조가 나중의 변경을 어렵게 하는지는 그 위에 변경을 시켜 봐야 압니다.
- **채점 스크립트를 네 군데 고쳤습니다.** 떨어진 항목은 모두 화면에서 확인했지만, 통과한 항목이 잘못 통과했을 가능성은 따로 확인하지 않았습니다.
- **결과물은 임시 폴더에 있어 남지 않습니다.**
