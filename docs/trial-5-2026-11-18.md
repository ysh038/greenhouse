# 실전 시험 5회: 프레임워크가 있을 때와 없을 때 (2026-11-18)

4회차까지 한 번도 하지 않은 비교입니다. **같은 모델이 같은 과제를 프레임워크가 있을 때와 없을 때 각각 만들면 결과가 얼마나 다른가.** 모델은 팀이 실제로 쓸 급인 Opus이고, 조건마다 3번씩 돌렸습니다.

## 요약

- **동작 품질에서는 차이가 없었습니다.** 여섯 번 모두 채점 24개(과제에 적힌 요구 12개, 적지 않은 견고성 12개)를 전부 통과했습니다. Opus는 프레임워크 없이도 늦게 온 응답 처리, 응답 검증, 키보드 접근, 중복 저장 방지를 스스로 챙겼습니다.
- **프레임워크 쪽이 더 느리고 비쌌습니다.** 시간은 약 2배, 토큰은 약 1.5배입니다.
- **코드의 모양은 달랐습니다.** 프레임워크 쪽은 직접 쓴 `useEffect`·리스너·타이머가 0이고, CSS가 10분의 1이며, 색을 직접 쓰지 않았습니다. 프레임워크 없는 쪽은 실행마다 색을 새로 정했습니다.
- **화면 평가는 평균이 같았습니다.** 조건을 가린 평가에서 두 조건 모두 평균 3.67점(5점 만점)입니다. 다만 프레임워크 쪽이 1등 하나와 꼴찌 둘을 차지해 편차가 컸습니다.
- **프레임워크 쪽 화면은 색과 글꼴은 같았지만 패널 배치가 셋 다 달랐습니다.** 프레임워크에 모달이 없어서 각자 만들었기 때문입니다. 프레임워크 없는 쪽은 세 번 모두 가운데 창으로 수렴했습니다.

이 시험이 보여 주는 것: **Opus에게 화면 하나를 맡기는 범위에서는, 이 프레임워크가 결과물의 품질을 높인다는 근거가 없습니다.**

## 시험 방법

### 과제

"식물 재고" 화면. 검색(300ms 지연), 목록, 상세 패널, 재고 수정, 불러오는 중·실패·빈 결과, Escape·바깥 클릭·닫기, 어두운 화면과 375px 지원. 화면에 보이는 글자까지 지시문에 적었습니다. 지시문은 두 조건이 경로만 다릅니다(`tools/compare/spec.md`).

### 조건

| | A: 프레임워크 있음 | B: 프레임워크 없음 |
|---|---|---|
| 출발점 | 이 저장소에서 기존 화면을 모두 지운 것 | 같은 스택의 일반적인 앱 (`tools/compare/baseline`) |
| 가진 것 | 안전한 API, 금지 규칙, UI 모듈, 화면 검증 | TanStack Query, 엄격한 TypeScript, typescript-eslint 권장 규칙, React Hooks 규칙, CSS 모듈, zod |
| 안내 | `CLAUDE.md`, README, 린트 메시지 | `CLAUDE.md`, README (규칙을 글로 적음) |
| 가짜 서버 | 같음 | 같음 |
| 모델, 횟수 | Opus, 3번 | Opus, 3번 |

- **예제 화면을 양쪽 다 없앴습니다.** 프레임워크 쪽이 기존 화면을 베낄 수 있으면 프레임워크의 효과와 예제의 효과가 섞입니다. 프레임워크 쪽에 불리한 조건입니다.
- 지시문에는 "실제 제품에 들어갈 코드라고 생각하고 만든다"고만 적었습니다. 견고성 항목은 알려 주지 않았습니다.

### 채점

구현을 모르는 스크립트(`tools/compare/accept.mjs`)가 브라우저에서 화면만 보고 검사합니다.

- **적힌 요구 12개**: 목록, 불러오는 중, 실패와 다시 시도, 검색 지연, 빈 결과, 패널과 포커스, 저장 성공과 2초 안내, 400 안내, 저장 중 비활성, 닫기 세 가지, 375px 넘침, 어두운 화면 명암비
- **적지 않은 견고성 12개**: 늦게 온 검색 응답, 깨진 응답, 상세 불러오기 실패, 빠르게 바꿔 누를 때의 상세, 400이 아닌 저장 실패, 키보드만으로 조작, 라벨 연결, 스크린 리더 알림, 안내 타이머 재시작, 연속 Enter, 밝은 화면 명암비, 콘솔 에러

## 해석

### 확인된 것

- **Opus는 이 정도 과제를 프레임워크 없이도 견고하게 만듭니다.** "에이전트는 `useEffect`로 데이터를 불러오며 경합을 만든다"는 전제는 이 모델, 이 과제에서는 성립하지 않았습니다. B는 TanStack Query와 zod로 경합과 깨진 응답을 처리했습니다. 다만 둘 다 B의 출발점에 이미 설치돼 있었고 README에 "서버 상태는 TanStack Query로 다룹니다"라고 적혀 있었으므로, B가 스스로 고른 것이 아닙니다. 이 유도가 없을 때 무엇을 쓰는지는 이 시험으로 알 수 없습니다.
- **프레임워크는 비용을 늘렸습니다.**
- **프레임워크는 구조를 같게 만들었습니다.** 같은 API, 직접 쓴 Effect 0, 색 0종. 다만 이것이 결과물의 품질 차이로 이어진다는 것은 이 시험에서 보이지 않았습니다.
- **프레임워크에 없는 것은 오히려 더 제각각이 됩니다.** 모달이 없으니 세 번 다 다른 것을 만들었고, `Button`의 제한 때문에 깨져 보이는 화면이 나왔습니다. 제한만 있고 대안이 없으면 결과가 나빠집니다.

### 확인되지 않은 것

프레임워크가 쓸모 있을 수 있는 경우들입니다. 어느 것도 이 시험으로는 알 수 없습니다.

- **화면이 쌓일 때**: B는 실행마다 색 15~19종을 새로 정했습니다. 화면 하나에서는 문제가 아니고, 스무 개가 되면 문제일 수 있습니다. 재지 않았습니다.
- **더 작은 모델**: 1~3회차에서 Haiku가 프레임워크의 린트 메시지만 보고 통과했습니다. Haiku가 프레임워크 없이 어떤 결과를 내는지는 재지 않았습니다. 프레임워크가 싼 모델의 품질을 Opus 수준으로 끌어올린다면 비용 면에서 가치가 있습니다.
- **나쁜 예제가 있는 코드베이스**: 두 조건 모두 빈 앱에서 시작했습니다. 실제 팀 코드에는 `useEffect` 141곳과 생 `<button>` 241곳이 있고, 에이전트는 주변 코드를 따라 합니다. 그때는 금지 규칙이 차이를 만들 수 있습니다.
- **모호한 과제**: 지시문이 화면의 글자까지 정해 줬습니다. 요구가 흐릴수록 결과가 갈릴 여지가 큽니다.
- **오래 유지할 때**: 색을 바꾸거나 다크 모드를 손볼 때의 비용.

## 한계

- **모든 화면이 만점이라 채점이 차이를 가르지 못했습니다.** 더 어려운 과제였다면 달랐을 수 있습니다.
- **채점 항목은 시험을 진행한 쪽이 골랐습니다.** 그리고 처음에는 프레임워크로 만든 기준 구현으로만 스크립트를 검증해서, B의 모달 패널을 잘못 채점했습니다(실패 3건). 하나씩 화면에서 직접 확인해 스크립트의 오류임을 확인하고 고친 뒤 여섯 개를 다시 채점했습니다.
- **조건이 섞였습니다.** 하위 에이전트에게 이 저장소의 `CLAUDE.md`가 자동으로 함께 전달됐습니다. B의 에이전트 둘은 그것을 보고도 과제 폴더의 안내를 따랐다고 보고했지만, 영향이 없었다고 확인할 수는 없습니다.
- **B도 브라우저로 직접 확인했습니다.** 에이전트 실행 환경에 브라우저 도구가 있어서 B의 세 에이전트 모두 개발 서버를 띄워 화면을 봤습니다. "화면 검증이 있는 A"와 "없는 B"의 비교가 아닙니다.
- **여섯 에이전트가 브라우저 창 하나를 같이 썼습니다.** 서로의 탭에 입력이 들어간 일이 보고됐습니다.
- 과제 하나, 조건당 3번입니다.
- B의 출발점과 README의 "규칙"은 시험을 진행한 쪽이 썼습니다.
- 화면 평가는 평가자 한 명(Opus), 한 번입니다.

## 재료

과제 지시문, 프레임워크 없는 조건의 출발점, 채점 스크립트는 `tools/compare`에 있습니다. 여섯 번의 결과물 자체는 저장소에 넣지 않았습니다.
