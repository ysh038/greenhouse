# 실전 시험 7회: 여러 에이전트가 동시에 만들 때 (2026-11-25)

5회차와 6회차에서는 프레임워크가 있든 없든 결과가 같았습니다. 남은 조건 가운데 둘을 한 번에 봤습니다: **여러 에이전트가 서로를 보지 못한 채 동시에 화면을 만드는 경우**와 **더 작은 모델(Sonnet)**. 이번에 새로 들어간 모달(`Dialog`, `ConfirmDialog`)과 구조 규칙도 처음으로 시험에 걸렸습니다.

## 요약

- **동작 품질은 이번에도 같았습니다.** 합친 앱에 채점 57개를 돌려 두 조건 모두 56개를 통과했고, 떨어진 항목도 같습니다.
- **화면 사이의 모양이 처음으로 갈렸습니다.** 프레임워크 없는 쪽은 세 화면의 "저장" 버튼이 높이, 모서리, 색이 서로 다르고, 한 화면은 브라우저 기본 모양 그대로입니다. 패널도 한 화면은 옆에서 나오고 다른 화면은 가운데에 뜹니다. 프레임워크 쪽은 재어 본 속성이 세 화면에서 모두 같습니다.
- **프레임워크 없는 쪽은 합친 뒤에도 정리하지 않았습니다.** 모달 구현이 두 벌 남았고 공용 폴더는 생기지 않았습니다. 6회차에서 Opus가 차례로 쌓을 때 스스로 공용으로 뺀 것과 다릅니다.
- **프레임워크 쪽이 더 비쌌습니다.** 토큰 1.8배입니다. 화면 검증과 스크린샷 검토가 그 안에 들어 있습니다.
- **구조 규칙의 위반은 이번에도 관측되지 않았습니다.** 두 조건 모두 기능 폴더 사이의 import가 0건입니다.

조건마다 한 번씩만 돌렸습니다. 모양이 갈린 원인이 모델인지 동시 작업인지는 이 시험으로 가를 수 없습니다.

## 시험 방법

### 구성

| | A (프레임워크 있음) | B (없음) |
|---|---|---|
| 출발점 | 이 저장소(커밋 `b1f395b`)에서 샘플 화면을 걷어 낸 것 | 같은 스택의 일반 앱. 데이터 라이브러리와 규칙 없음 |
| 가짜 서버, 테스트 도우미 | 프레임워크의 것 | 같은 것을 앱 안에 복사해 둠 |
| `pnpm check` | 7단계 (화면 검증과 스크린샷 검토 포함) | 타입 검사, 린트, 테스트, 빌드 |

1. 조건마다 출발점을 세 벌 복사하고, Sonnet 에이전트 셋이 **동시에** 주문, 공급처, 알림 설정 화면을 하나씩 만듭니다. 서로의 복사본은 볼 수 없습니다. 각자 메뉴도 만듭니다.
2. 세 화면이 끝나면 네 번째 Sonnet 에이전트가 세 복사본을 앱 하나로 합칩니다. 지시문에는 "동작과 글자는 각 복사본과 같아야 한다"고만 적었고, 공용으로 정리하라는 말은 넣지 않았습니다.

화면 과제는 6회차의 것을 그대로 썼습니다(`tools/compare/concurrent/specs`). 에이전트는 조건마다 4개, 모두 8개입니다.

### 채점과 측정

- **화면 채점 57개**: 6회차의 스크립트(주문 21, 공급처 19, 알림 설정 17)를 합친 앱에 돌렸습니다. 앱이 실제 HTTP 요청을 보내는 구조로 바뀌어서, 스크립트가 가짜 서버를 직접 조작하던 부분을 요청 가로채기로 옮겼습니다.
- **화면 사이의 모양**: 세 화면의 "저장" 버튼과 입력란에서 계산된 스타일 8가지(높이, 모서리, 배경색, 글자색, 글자 크기와 굵기, 테두리색, 안쪽 여백)를 비교했습니다.
- **코드 측정**: 줄 수, 직접 쓴 Effect·리스너·타이머, 모달을 직접 구현한 파일, 기능 폴더 사이의 import(프레임워크의 구조 규칙을 B에도 돌림).
- `pnpm check`는 합친 앱에서 진행자가 직접 다시 돌렸습니다.

### 화면 사이의 모양

세 화면에서 값이 서로 다른 속성의 수입니다(8가지 중).

| | A | B |
|---|---|---|
| "저장" 버튼 | 0 | 7 |
| 입력란 | 0 | 5 |

B의 "저장" 버튼은 이렇게 달랐습니다.

| | 주문 | 공급처 | 알림 설정 |
|---|---|---|---|
| 높이 | 44px | 40px | 40px |
| 모서리 | 8px | 0px | 6px |
| 배경색 | 초록 `rgb(31, 111, 74)` | 회색 `rgb(239, 239, 239)` (브라우저 기본) | 초록 `rgb(31, 111, 67)` |
| 글자 굵기 | 600 | 400 | 400 |

- B의 주문 상세는 화면 오른쪽에서 나오는 패널이고, 공급처 추가는 가운데에 뜨는 창입니다. A는 둘 다 가운데에 뜨는 같은 창입니다.
- B의 합치기 에이전트는 이 차이를 알고 있었고, 보고서에 "화면별 버튼과 입력란의 모양은 서로 다릅니다. 각 복사본의 스타일을 그대로 두었고 통일하지 않았습니다"라고 적었습니다.
- A의 일치는 에이전트가 맞춘 것이 아니라 같은 컴포넌트를 썼기 때문입니다. 세 에이전트는 서로를 보지 못했습니다.

스크린샷을 직접 봐도 차이가 뚜렷해서, 조건을 가린 평가는 따로 하지 않았습니다.

## 관측된 것

- **A의 스크린샷 검토가 실제 결함을 잡았습니다.** 주문 에이전트는 발송 처리 뒤 포커스가 창 밖으로 빠져 Escape가 먹지 않는 것을, 공급처 에이전트는 안내 문구가 뜰 때 목록이 24px 밀리는 것을 화면 검증에서 찾아 고쳤다고 보고했습니다. 진행자가 따로 재현해 확인하지는 않았습니다.
- **여섯 에이전트 모두 지시문에 없는 실패 문구를 만들었습니다.** "저장하지 못했습니다" 계열이고 문장은 제각각입니다. 지시문이 그 경우를 정하지 않았습니다.
- **가짜 서버 플러그인의 결함이 드러났습니다.** 화면이 요청을 취소하면 개발 서버가 오류 화면을 띄웠습니다. 에이전트 셋이 보고했고, B의 에이전트 둘은 화면 코드를 바꿔 피했습니다. 시험 뒤에 재현해 고쳤습니다(`apps/sample/fakeServer.plugin.mjs`).
- **A의 화면 검증이 부하 속에서 헛돌았습니다.** 에이전트 둘이 한 번씩 이유 없는 실패를 겪고 다시 돌려 통과했습니다.
- **구조 규칙은 걸린 적이 없습니다.** 화면이 서로의 코드를 쓸 일이 없는 과제였고, 합친 뒤에도 두 조건 모두 0건입니다. 이 규칙은 아직 위반이 관측되지 않은 채 들어가 있습니다.
- **5회차와 6회차에서 체인마다 달랐던 모달이 A에서는 같아졌습니다.** 서로를 보지 못한 두 에이전트가 같은 `Dialog`와 `ConfirmDialog`를 썼습니다.

## 한계

- **조건마다 한 번입니다.** 같은 조건을 다시 돌리면 달라질 수 있습니다.
- **바뀐 조건이 둘입니다.** 6회차와 견주면 모델(Opus → Sonnet)과 방식(차례로 → 동시에)이 같이 바뀌었습니다. B가 정리하지 않은 것이 어느 쪽 때문인지 가를 수 없습니다.
- **합치기 지시문이 정리를 요구하지 않았습니다.** "각 복사본과 같아야 한다"는 문장이 B의 합치기 에이전트가 모양을 통일하지 않은 이유일 수 있습니다. 사람이 합쳤다면 맞췄을 차이입니다.
- **화면이 서로 독립입니다.** 한 화면이 다른 화면의 데이터나 컴포넌트를 필요로 하는 과제가 아니어서, 구조 규칙이 걸릴 상황이 만들어지지 않았습니다.
- **채점 스크립트를 옮긴 뒤 처음 쓴 것입니다.** 떨어진 한 항목은 구현한 에이전트의 보고와 일치해 채점 오류가 아닌 것을 확인했습니다. 통과한 항목이 잘못 통과했을 가능성은 따로 확인하지 않았습니다.
- **결과물은 임시 폴더에 있어 남지 않습니다.** 지시문, 출발점, 측정 스크립트는 `tools/compare/concurrent`에 있습니다.

## 다음에 볼 것

- 화면이 서로 엮이는 과제(한 화면이 다른 화면의 목록을 고르는 식)여야 구조 규칙의 위반을 볼 수 있습니다.
- 줄마다 있는 버튼의 접근 이름은 두 조건이 똑같이 놓쳤습니다. 린트로 잡을 수 있는지 볼 만합니다.
