# 실전 시험 3회 (2026-11-18)

UI 모듈을 만든 뒤 처음 하는 시험입니다. 세 가지를 봤습니다.

1. UI 모듈의 금지 메시지 네 개가 메시지만으로 통하는가.
2. 프레임워크에 맞는 API가 없을 때 메시지가 도움이 되는가. 2회차의 한계로 남겨 둔 것입니다.
3. 메시지를 고치면 결과가 실제로 달라지는가. 같은 과제를 세 번 돌렸습니다. 1차는 처음 상태, 2차는 메시지를 고친 뒤, 3차는 제품 CSS 검사를 넣은 뒤입니다.

## 요약

- **세 번 모두 통과했습니다.** 작은 모델(Haiku) 에이전트가 린트 에러 23건을 없애고 동작 테스트 7개를 통과시켰습니다. 각각 약 1분 40~50초 걸렸습니다.
- **대안이 없는 경우**: 체크박스 컴포넌트가 없자 에이전트는 메시지 안내대로 프레임워크에 `Checkbox`를 추가했습니다. API는 미리 만들어 둔 정답과 같은 모양이었지만 테스트 없이 추가됐고, `pnpm check`는 이를 막지 못했습니다.
- **메시지 수정의 효과는 하나만 확인됐습니다.** `<input>` 메시지에 `Checkbox`를 적은 뒤에는 새로 만들지 않고 있는 것을 썼습니다. 고정 `style` 메시지에 "토큰 변수를 쓴다"를 적은 것은 결과를 바꾸지 못했습니다.
- **제품 CSS가 열린 문이었습니다.** 두 번 모두 제품 폴더에 CSS 파일이 생겼고 고정 px가 들어갔습니다. 2차에서는 프레임워크 `Button`의 모양을 제품 CSS로 덮어썼습니다. 2차 뒤에 이를 막는 검사(stylelint)를 넣었고, 3차에서 에이전트가 쓴 `8px`을 검사가 잡아 토큰으로 고치게 했습니다. 3차의 제품 CSS에는 덮어쓰기도 고정 px도 남지 않았습니다.
- **교정**: 2차 3건(모두 제품 CSS), 3차 0건. 다만 3차 결과에는 검사로 잡을 수 없는 화면상의 차이가 2곳 있었습니다.

## 시험 방법

- **주어진 코드**: 구성원 초대 화면을 기존 방식으로 짠 파일 하나. 생 `<button>` 4개, 생 `<input>` 2개(글자 입력과 체크박스), 고정 값이 든 `style` 15곳, `li`와 `div`의 `onClick` 2곳.
- **출발 상태**: 린트 에러 23건, 동작 테스트 7개 중 3개 실패.
- **숨겨 둔 버그**: 폼 안의 "지우기" 버튼에 `type`이 없어서 누르면 폼이 제출됩니다. 실패하는 테스트 중 하나가 이것입니다.
- **대안이 없는 것**: 체크박스. 1차 시험 때 프레임워크에 `Checkbox`가 없었습니다.
- **동적 값과 고정 값이 섞인 것**: 사용량 막대. 너비는 실행 중에 정해지고 높이와 모서리는 고정입니다.
- **성공 기준**: `pnpm check` 통과. 테스트는 미리 써 두었고 고칠 수 없게 했습니다.
- **기준 검증**: 정답을 먼저 구현해 테스트 7개가 통과하는 것을 확인한 뒤, 정답을 치우고 기존 방식 코드로 바꿔 넣었습니다.
- **읽기 제한**: 2회차와 같습니다. 규칙 파일, 위반 예제, 프레임워크 테스트, 문서, 샘플 앱의 다른 기능은 읽지 못하게 했고 프레임워크 구현 소스는 허용했습니다.
- **수정 범위**: 화면 폴더 안. 린트 메시지가 다른 위치에 추가하라고 명시하면 따라도 된다고 했습니다.

세 번 모두 같은 지시문, 같은 출발 코드, 서로 다른 새 에이전트입니다. 2차에서 달라진 것은 1차 뒤에 반영한 메시지 두 개와 `Checkbox`의 존재이고, 3차에서 달라진 것은 제품 CSS 검사입니다.

읽기 제한은 지시일 뿐 기술적으로 막은 것이 아닙니다. 세 에이전트 모두 금지된 것을 읽지 않았다고 보고했고, 이는 확인할 수 없습니다.

### 교정 3건 (2차 결과)

모두 `pnpm check`를 통과한 코드였고, 손으로 고쳤습니다.

1. 제품 CSS의 `li > button { width: 100%; justify-content: flex-start }`를 지웠습니다. 프레임워크 컴포넌트는 `className`을 받지 않게 만들었는데, 바깥에서 요소 선택자로 덮어쓰면 그 제한이 의미가 없어집니다.
2. 폼 배치를 제품 CSS(`display: flex; gap`)에서 `Stack`으로 바꿨습니다.
3. 막대 높이 `8px`을 `var(--gh-space-sm)`으로 바꿨습니다.

말풍선 너비 `240px`은 맞는 토큰이 없어 그대로 뒀습니다.

### 시험 뒤에 넣은 제품 CSS 검사

에이전트가 만든 CSS 원본을 보관해 두었다가 새 검사를 돌려 봤습니다.

| 대상 | 검사 결과 |
|---|---|
| 1차의 제품 CSS | `height: 8px` 1건 |
| 2차의 제품 CSS | `height: 8px`, `.memberRow > button` 2건 |
| 1차에서 프레임워크에 추가된 `Checkbox`의 CSS | `16px` 2건 |

교정 3건 중 1번과 3번은 이제 검사가 잡습니다. 2번(배치를 `Stack` 대신 CSS로 한 것)은 잡지 못합니다. `240px`은 통과합니다.

### 3차 결과에서 본 것

검사에 걸리는 것은 남지 않았습니다. 대신 브라우저에서 띄워 보니 검사로는 알 수 없는 차이가 2곳 있었습니다.

- 말풍선에 배경과 테두리가 없어 글자만 떠 있습니다. 아래에 다른 내용이 있으면 겹칩니다.
- "(관리자)" 표시가 버튼 밖으로 나가 이름과 떨어져 보입니다. 버튼의 이름에서도 빠졌습니다.

둘 다 테스트와 린트는 통과합니다. 화면을 직접 봐야 알 수 있는 종류이고, 3단계 검증 도구(에이전트가 화면을 띄워 스크린샷을 남기는 것)가 맡을 영역입니다.

샘플 앱에는 3차 결과가 아니라 2차 결과를 교정한 판을 남겼습니다. 브라우저에서 확인해 둔 것이 그 판이기 때문입니다.

## 반영 후 확인

- `pnpm check` 6단계 통과 (테스트 97개).
- 브라우저에서 확인한 것: 사용량 막대가 60% 너비로 보임, 구성원을 누르면 선택 표시와 "내보내기"가 나옴, "자리란?"을 누르면 말풍선이 열리고 바깥을 누르면 닫힘.
- 브라우저에서 확인하지 못한 것: 초대와 지우기, 입력 오류 표시, 자리가 다 찼을 때의 막대 색. 테스트로만 확인했습니다.

## 한계

- 각 조건을 한 번씩만 돌렸습니다. 달라진 것이 조치 때문인지 실행마다의 편차인지 구분할 수 없습니다. 원인이 분명한 것은 체크박스(컴포넌트가 생겼음)와 3차의 `8px`(검사에 걸려 고쳤다고 보고함) 둘입니다. 3차에서 덮어쓰기가 나오지 않은 것은 검사 덕인지 알 수 없습니다. 1차에서도 나오지 않았습니다.
- 2차에는 변수가 두 개 섞였습니다. 메시지 수정과 `Checkbox`의 존재입니다.
- 3번 메시지 수정은 효과가 없었습니다. 메시지로는 제품 CSS의 값을 통제하지 못한다는 뜻으로 읽고, 4번(검사)으로 옮겨야 한다고 판단했습니다. 이 판단은 2번의 실행에 근거한 것입니다.
- 이번에도 정답이 있는 옮기기 과제입니다. 새 화면을 UI 모듈로 처음부터 만드는 시험은 하지 않았습니다.
- 2회차에서 고친 Effect·데이터 메시지 세 개는 이번에도 다시 시험하지 않았습니다.
