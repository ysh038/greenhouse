# 실전 시험 4회 (2026-11-18)

검증 도구(`pnpm verify`)를 만든 뒤 처음 하는 시험입니다. 두 가지를 봤습니다.

1. **검토 시험**: 에이전트가 스크린샷만 보고 화면 결함을 알아채는가. 검증 도구가 쓸모 있으려면 성립해야 하는 가정입니다.
2. **새 화면 시험**: 맥락 없는 에이전트가 새 화면을 처음부터 만들 때, 시키지 않아도 시나리오를 쓰고 스크린샷을 확인하는가. 3회차까지는 모두 정답이 있는 옮기기 과제였습니다.

## 요약

- **큰 결함은 스크린샷으로 잡힙니다.** 정보가 화면에서 사라지는 결함은 세 모델 모두 찾았고, "내보내도 되는가"라는 최종 판단은 다섯 번 모두 맞았습니다.
- **검토는 모델이 클수록 낫습니다.** Opus만 없는 문제를 지어내지 않았고, 심지 않은 실제 CSS 버그를 하나 찾았습니다. 처음에는 Haiku와 Sonnet만 돌리고 결론을 냈는데, 그 순서가 틀렸습니다.
- **그래도 미세한 결함은 세 모델 모두 못 잡았습니다.** 간격이 조금 어긋난 결함은 Haiku와 Opus가 놓쳤고 Sonnet은 취향 문제로 넘겼습니다. 원래 어떻게 보여야 하는지 기준이 없으면 알아챌 수 없는 종류입니다.
- **`CLAUDE.md`의 한 문단이 통했습니다.** 새 화면 시험에서 에이전트는 지시문에 없던 시나리오를 쓰고 스크린샷을 열어 봤습니다. 다만 24장 중 4장만 봤습니다.
- **새 화면은 교정 1건으로 끝났습니다.** `pnpm check`가 통과했고 탈출구는 없었습니다. 교정은 에이전트가 스크린샷에서 직접 발견해 보고한 정렬 문제이고, 원인이 프레임워크에 있어 API로 옮겼습니다.
- **프레임워크의 빈 곳 일곱 개가 드러났습니다.** 그중 세 개를 반영했습니다.

## 1. 검토 시험

### 방법

- 구성원 초대 화면에 결함 세 개를 심었습니다. 셋 다 `pnpm check`(타입, 린트, 테스트, 화면 검증의 자동 검사)를 통과합니다.
- 리뷰어 에이전트에게 소스 코드를 읽지 못하게 하고, 스크린샷 18장과 보고서만으로 "이 화면을 내보내도 되는가"를 판단하게 했습니다.
- 결함이 있다는 것은 알려 주지 않았고, "문제가 없으면 없다고 보고하라"고 했습니다.
- 대조로, 결함이 없는 판을 같은 지시문으로 한 번 더 검토하게 했습니다.
- 처음에는 Haiku(결함 판, 대조)와 Sonnet(결함 판)만 돌렸습니다. "작은 모델이라 놓친 것 아니냐"는 지적을 받고 Opus(결함 판, 대조)를 추가했습니다.

| 심은 결함 | 보이는 곳 | 검사를 통과하는 이유 |
|---|---|---|
| A. 선택 표시의 글자색이 고정이라 안 보임 | 어두운 화면 | `style` 안의 조건식에 든 색은 규칙에 안 걸림 (3회차 문서의 7번) |
| B. 말풍선에 배경이 없고 넓어서 아래 글자와 겹침 | 좁은 화면 | 모양은 검사 대상이 아님 |
| C. "(관리자)"가 버튼 밖으로 나가 떨어져 보임 | 모든 화면 | 모양은 검사 대상이 아님. 3회차 3차에서 실제로 나온 결함 |

세 결함이 스크린샷에 보이는 것은 시험 전에 직접 확인했습니다.

### 결과

결함 판:

| | Haiku | Sonnet | Opus |
|---|---|---|---|
| A. 어두운 화면에서 글자가 안 보임 | 찾음. "내보내면 안 됨" | 찾음. "내보내면 안 됨" | 찾음. "내보내면 안 됨" |
| B. 좁은 화면에서 겹침 | 반쯤. 그 말풍선을 지적했지만 정렬 문제로 봄 | 찾음. 겹친다고 설명 | 찾음. 넓은 화면에서 배경과 테두리가 없다는 것까지 지적 |
| C. "(관리자)"가 떨어짐 | 놓침 | 약하게. "간격이 행마다 다름, 취향 차이" | 놓침 |
| 최종 판단 | 내보내면 안 됨 (맞음) | 내보내면 안 됨 (맞음) | 내보내면 안 됨 (맞음) |
| 없는 문제를 지적 | 1건 (라벨이 흐리다고 함. 실제로는 정상 대비) | 0건 | 0건 |
| 걸린 시간 | 약 45초 | 약 53초 | 약 65초 |

결함 없는 판 (대조):

| | Haiku | Opus |
|---|---|---|
| 최종 판단 | 내보내도 됨 (맞음) | 내보내도 됨 (맞음) |
| 없는 문제를 지적 | 1건 (말풍선이 라벨을 덮는다고 함. 실제로는 옆에 붙어 있음) | 0건. "겹침, 잘림, 넘침 없음"이라고 명시 |
| 심지 않은 실제 문제를 찾음 | 다른 화면의 긴 이름 줄바꿈 | 선택한 줄의 테두리가 단계마다 다름(실제 CSS 버그), "내보내기"가 파일 저장으로 읽힘, 다른 화면의 긴 이름 줄바꿈 |

- Haiku의 없는 문제 지적 2건은 모두 "고치면 좋음"으로 낮게 매겨졌고 최종 판단을 뒤집지 않았습니다.
- 다섯 에이전트 모두 18장을 전부 열어 봤다고 보고했습니다. 확인할 방법은 없습니다.
- Sonnet과 Opus는 `pnpm verify`를 직접 돌리지 않고 보관해 둔 증거 폴더를 받았습니다. 지시문이 그만큼 다릅니다.
- Sonnet으로는 대조를 돌리지 않았습니다.

### Opus가 찾은 실제 버그

선택된 버튼 위에 마우스가 있으면 선택 테두리가 사라졌습니다. 호버 규칙의 우선순위가 선택 상태 규칙보다 높았기 때문입니다. 결함을 심지 않은 판에서 나온 지적이고, 프레임워크의 `Button` CSS를 고쳤습니다. Opus는 이것을 "포커스가 엉뚱한 곳에 있는 것 같다"고 추측했는데, 원인은 달랐지만 증상은 정확했습니다.

### 해석

- "내보내도 되는가"를 가르는 용도로는 쓸 만합니다. 사용자가 정보를 못 보게 되는 결함은 작은 모델도 잡았습니다.
- 검토에는 큰 모델을 쓰는 것이 맞습니다. 정확도(없는 문제를 지어내지 않음)와 깊이(심지 않은 버그를 찾음) 모두 Opus가 나았습니다. 검토 한 번의 토큰 양은 세 모델이 비슷했습니다(약 8만 5천).
- 모델을 키워도 안 되는 것이 있습니다. 결함 C는 3회차에서 실제로 나왔던 것인데 세 모델 모두 사실상 걸러 내지 못했습니다. 무엇이 맞는 모양인지 기준이 스크린샷 안에 없기 때문으로 보입니다.
- 결함 C는 시나리오가 버튼의 이름을 정확히 요구하면 자동으로 잡힙니다(3회차 결과물로 확인함). 미세한 결함은 눈보다 시나리오의 대상 지정이 더 잘 잡는다는 뜻입니다.

## 2. 새 화면 시험

### 방법

- 과제: 샘플 앱에 "작업" 화면을 처음부터 만들기. 가짜 서버 라우트 4개, 상태 필터, 완료 체크, 확인을 거치는 삭제, 추가 폼, 불러오는 중·실패·빈 목록 화면.
- 프레임워크에 없는 것이 필요하도록 골랐습니다. 상태 필터(세그먼트나 라디오), 삭제 확인(모달), 완료된 항목의 표시.
- 지시문에는 "`CLAUDE.md`를 읽고 따르라"고만 했습니다. 시나리오를 쓰라거나 스크린샷을 보라는 말은 넣지 않았습니다.
- 읽기 제한은 없습니다. 시험 기록 문서만 읽지 못하게 했습니다.
- 모델은 Sonnet입니다.

### 결과

| 항목 | 결과 |
|---|---|
| `pnpm check` | 통과 (직접 다시 실행). 테스트 97 → 111개, 스크린샷 33 → 57장 |
| 걸린 시간, 도구 호출 | 약 5분 42초, 22회 |
| 새로 만든 파일 | 화면, 데이터 정의, 테스트 14개, 시나리오 |
| 고친 파일 | 가짜 서버, `App.tsx`, 프레임워크의 `Checkbox`(속성 1개와 테스트 1개) |
| 탈출구, 설정 수정 | 0건 |
| 린트·타입 에러 | 0건 (한 번에 통과했다고 보고) |
| 시나리오 | 시키지 않았는데 씀. 8단계 |
| 열어 본 스크린샷 | 24장 중 4장 (에이전트 보고) |
| 교정 | 1건 |

바뀐 범위는 시험 전 백업과 비교해 확인했고, 스크린샷은 에이전트가 열지 않은 것을 포함해 직접 봤습니다.

### 검증 고리가 돈 부분

- 에이전트가 스크린샷(빈 제목 오류 상태)에서 "오류 문장이 나오면 추가 버튼이 입력란과 어긋난다"는 것을 발견해 보고했습니다. 고치지는 않았습니다.
- 화면 검증의 자동 검사가 시나리오의 모호한 대상("추가" 버튼이 페이지에 둘)을 잡았고, 에이전트는 시나리오를 고쳤습니다.

### 교정 1건

오류 문장이 나올 때 버튼이 어긋나는 것. `TextField`와 `Button`을 `Stack`으로 나란히 놓으면 생기는 문제라 화면 코드가 아니라 프레임워크의 문제입니다. `TextField`에 `trailing` 속성을 넣어 버튼을 입력란과 같은 줄에, 오류 문장을 그 아래에 두게 했습니다.

### 드러난 빈 곳

| 번호 | 빈 곳 | 에이전트가 한 것 | 조치 |
|---|---|---|---|
| 1 | 완료된 항목을 구분해 보여 줄 방법이 `Checkbox`에 없음 | 프레임워크의 `Checkbox`에 `isStruck` 속성을 추가하고 테스트를 씀. 제품 CSS로 덮어쓰지 않음 | 그대로 채택 |
| 2 | 입력란 옆에 버튼을 놓으면 오류 문장이 나올 때 어긋남 | 발견해 보고만 함 | `TextField`의 `trailing` 속성. 반영 |
| 3 | 시나리오에서 대상을 구역 안으로 좁힐 수 없음 | Enter 키로 제출하고, 단계 순서를 바꿔 피함 | 대상 지정의 `within`. 반영 |
| 4 | 하나만 고르는 필터 컴포넌트가 없음 | `Button`에 `aria-pressed`를 줘서 만듦 | 미반영. 한 번 관측 |
| 5 | 삭제 같은 위험한 동작용 버튼 모양이 없음 | "삭제 확인"을 주된 동작 모양(녹색)으로 만듦 | 미반영. 한 번 관측 |
| 6 | 모달이 없음 | 줄 안에 확인 문구를 펼침 | 미반영. 결과가 나쁘지 않음 |
| 7 | 가짜 서버에 데이터를 처음으로 되돌리는 수단이 없음 | 샘플 앱의 가짜 서버 파일에 되돌리는 함수를 따로 만듦 | 미반영 |

1번은 3회차에서 넣은 안내("속성으로 안 되는 모양은 컴포넌트에 속성을 추가하고 테스트를 같이 쓴다")대로 된 것입니다. 3회차 1차에서는 테스트 없이 추가됐었습니다. 다만 이번에는 읽기 제한이 없었고 모델도 달라서, 안내 덕분인지는 알 수 없습니다.

## 시험 뒤에 고친 것

- **`within`**: 시나리오의 대상을 다른 요소 안으로 좁힙니다.
- **화면 조건 동시 실행**: 시나리오가 3개가 되자 화면 검증이 76초 걸렸습니다. 세 화면 조건을 동시에 돌리게 해서 28초로 줄였습니다.
- **`TextField`의 `trailing`**: 위의 교정.
- **`Button`의 선택 테두리**: Opus가 찾은 버그.

고친 뒤 `pnpm check`는 통과합니다(테스트 112개, 스크린샷 57장). `trailing`으로 바꾼 화면은 스크린샷으로 확인했습니다.

## 한계

- 조건마다 한 번씩 돌렸습니다. 모델 간 차이가 모델 때문인지 실행마다의 편차인지 구분할 수 없습니다. "Opus가 낫다"는 것도 두 번의 실행에 근거한 것입니다.
- 결함은 제가 골라 심었습니다. 스크린샷으로 잘 보이는 것을 골랐을 수 있습니다.
- 검토 시험은 화면 하나, 스크린샷 18장입니다. 화면이 많아지면 리뷰어가 전부 열어 보는지는 보지 않았습니다. 새 화면 시험의 에이전트는 자기 화면의 24장 중 4장만 봤습니다.
- 새 화면 시험은 Sonnet 한 번입니다. 3회차까지 쓴 Haiku로는 돌리지 않았습니다.
- 화면을 만든 에이전트와 검토하는 에이전트를 이어서 돌려 보지는 않았습니다. 만든 쪽이 놓친 것을 검토 쪽이 잡는지는 따로 봐야 합니다.

## 다음에 볼 것

- **스크린샷을 전부 보게 하는 장치**: 지금은 `CLAUDE.md`의 문장뿐입니다. 만든 에이전트는 일부만 봤습니다.
- **미세한 결함**: 모델을 키워도 스크린샷 검토로는 약했습니다. 기준이 필요한 종류라, 이전 실행의 스크린샷과 비교해 달라진 곳만 보여 주는 방식이나 시나리오의 대상 지정을 엄격하게 하는 방식이 후보입니다.
- **팀 프로젝트의 실제 화면**: 빈 곳 일곱 개가 과제 하나에서 나왔습니다. 실제 화면에서는 더 많을 것입니다.
