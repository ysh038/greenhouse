# 실전 시험 1회 (2026-11-18)

이 저장소의 맥락을 모르는 새 에이전트에게 샘플 앱 기능 하나를 맡기고, 프레임워크와 린트만으로 옳은 코드가 나오는지 봤습니다.

## 요약

- **교정할 코드는 0건이었습니다.** 금지 패턴(`useEffect`, 타이머, `addEventListener`, `fetch`, `@tanstack/react-query`)과 탈출구(`eslint-disable`, `@ts-ignore`, `any`, `as`, `!`)가 하나도 없었습니다.
- **규칙이나 설정을 약하게 고치지 않았습니다.** 시험 전 백업과 비교하니 바뀐 것은 `apps/sample/src` 안의 파일뿐이었습니다.
- **린트 메시지가 길을 안내하는지는 검증되지 않았습니다.** 에이전트가 코드를 쓰기 전에 모듈의 `lint.mjs`와 `*.good.tsx` 예제를 읽어서, 린트 에러를 한 번도 만나지 않았습니다.
- **프레임워크에서 고칠 것을 8가지 찾았고, 7가지를 반영했습니다.** 아래 "프레임워크 개선 항목"에 있습니다.

## 과제

샘플 앱에 "사용자" 섹션 추가. 프레임워크 사용법이나 금지 규칙에 대한 힌트는 주지 않았습니다.

1. 300ms 디바운스 검색
2. 목록 조회와 로딩·실패 화면
3. 바깥 클릭과 Escape로 닫히는 상세 패널, 열릴 때 이름 입력란 자동 포커스
4. 이름 수정 저장, 목록 반영, "저장했습니다" 문구 2초 표시, 빈 이름은 400
5. 창 너비 표시와 갱신

자동 포커스는 일부러 넣은 빈틈입니다. 프레임워크에 맞는 훅이 없습니다.

## 결과

| 항목 | 결과 |
|---|---|
| 추가·수정 파일 | `apps/sample/src` 안 8개(새 파일 6개). 밖은 0개 |
| 금지 패턴, 탈출구 | 0건 |
| 에이전트가 만난 린트·타입 에러 | 0건 |
| 에이전트가 쓴 테스트 | 11개 |
| `pnpm check` | 통과 (직접 다시 실행해 확인) |
| 브라우저 확인 | 다섯 기능 모두 동작. 아래 한 가지는 불확실 |

브라우저에서 직접 확인한 것: 목록 5명 표시, "김" 검색 시 2명, 패널 열림과 자동 포커스, 안쪽 클릭 유지, Escape와 바깥 클릭으로 닫힘, 이름 저장 후 목록 반영, 안내 문구가 1.6초에는 보이고 2.8초에는 사라짐, 빈 이름 저장 시 400 안내.

**불확실한 것**: 창 너비 표시는 화면 크기를 700px, 500px로 바꿨을 때는 맞게 갱신됐습니다. 원래 크기에서 640px로 바꾼 두 번은 이전 값(1024px)이 남아 있었습니다. 브라우저 도구의 화면 크기 흉내 기능이 원래 크기에서 벗어나는 순간에만 생기는 현상으로 보이지만, 실제 창을 끌어서 확인하지는 못했습니다.

## 에이전트가 고른 방법

빈틈과 제약을 만났을 때 규칙을 우회하지 않고 아래처럼 풀었습니다.

- **자동 포커스**: Effect 대신 `<input autoFocus>`와 `key={선택한 사용자}`로 패널을 새로 만들기
- **2초 안내 문구**: `key={저장 횟수}`로 안내 컴포넌트를 새로 만들어 매번 2초를 새로 세기
- **창 너비**: `useState(() => window.innerWidth)`와 `useEventListener(window, 'resize', ...)`
- **검색어가 바뀔 때 에러 상태 풀기**: `<DataBoundary key={검색어}>`로 통째로 다시 만들기

## 프레임워크 개선 항목

에이전트의 보고와 코드 검토에서 나온 것입니다. 원칙대로 규칙 파일이 아니라 API나 규칙으로 옮깁니다.

| 번호 | 문제 | 옮긴 곳 | 상태 |
|---|---|---|---|
| 1 | `DataProvider` 기본값이 실패를 한 번 재시도함. 404나 스키마 불일치도 재시도한 뒤에야 실패 화면이 뜸 | 4xx 응답과 스키마 오류는 재시도하지 않음. 5xx, 408, 429, 네트워크 오류만 한 번 재시도 | 반영 |
| 2 | `DataBoundary`에 에러를 푸는 수단이 없어 `key`로 통째로 다시 만들어야 함 | `DataBoundary`의 `resetKeys` 속성 | 반영 |
| 3 | 검색어가 바뀔 때마다 목록이 "불러오는 중"으로 깜빡임. 이전 결과를 유지할 방법이 없음 | `useDeferredData`. 새 결과가 올 때까지 이전 결과를 유지하고 `isUpdating`으로 알려 줌 | 반영 |
| 4 | 가짜 서버가 제품 구역에 있어 `setTimeout`을 못 씀. 로딩과 실패 화면을 브라우저에서 볼 방법이 없음 | `@agent-greenhouse/framework/fake-api`의 `createFakeApi`. 지연 시간, `failOnce`, `hangOnce`, 요청 기록 | 반영 |
| 5 | 제품 코드 테스트의 선례가 없음. 가짜 타이머와 조회를 같이 쓰려면 요령이 필요함 | `@agent-greenhouse/framework/testing`의 `renderWithData`, `advanceTime` | 반영 |
| 6 | `useMutate`의 `error`가 `unknown`이라 실패 여부를 `error !== null`로 판단해야 함 | `useMutate`의 `isError` | 반영 |
| 7 | 배치 수단과 공용 실패 화면이 없어 인라인 `style`과 중복 컴포넌트가 생김 | `@agent-greenhouse/framework/ui`의 `Stack`(배치), `ErrorNotice`(공용 실패 화면)와 고정 값 인라인 `style` 금지 | 반영 (시험 뒤에 추가) |
| 8 | `useTimeout`은 지연 시간이 바뀔 때만 다시 예약함. 같은 시간으로 다시 시작하려면 `key`로 새로 만들어야 함 | `useTimeout`의 세 번째 인자 `restartKey` | 반영 |

## 반영 후 확인

- 시험에서 에이전트가 만든 화면과 테스트를 새 API로 옮겼습니다. 에이전트가 테스트에 직접 만들었던 도우미 세 개(실패 한 번 시키기, 시간 진행, 조회 환경에서 렌더)는 프레임워크 도구와 같은 모양이어서 그대로 대체됐습니다.
- 브라우저에서 확인한 것: 처음 진입할 때 "불러오는 중"이 보임. 검색어를 바꾸면 이전 목록 5명이 유지되다가 결과 2명으로 바뀌고, 그 사이 "불러오는 중"으로 깜빡이지 않음.
- 브라우저에서 확인하지 못한 것: 목록 실패 화면과 `resetKeys`로 에러가 풀리는 흐름. 테스트로만 확인했습니다.
